# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
go mod tidy
go run ./cmd/bot             # needs BOT_TOKEN; auto-creates ./bot.db
go test -race ./...
gofmt -l .                   # must be empty before committing
make build | run | test | vet | docker-up | docker-down | docker-logs

docker compose up -d --build
docker compose logs -f
```

Bot version is stamped via `-ldflags "-X main.version=$(git describe ...)"` — `make build`/`make docker-up` and `scripts/auto-deploy.sh` do it automatically; a bare `docker compose up -d --build` yields `dev`.

Config is env-only — no config file. Required: `BOT_TOKEN`. Optional: `CAPTCHA_TIMEOUT_SECONDS` (30), `MAX_ATTEMPTS` (3), `NEWCOMER_DAYS` (7), `SILENT_ANNOUNCE_DAYS` (30, 0=off), `LOG_LEVEL` (info), `DB_PATH` (bot.db / /data/bot.db in Docker), `ALLOWED_CHATS` (none = all chats), `OWNER_IDS`, `LOG_FILE` (set in Docker to /data/bot.log), `CAPTCHA_DELAY_MS` (2000), `DAILY_STATS_UTC_HOUR` (6), `GROQ_API_KEY` + `GROQ_MODEL` (llama-3.1-8b-instant), `GIGACHAT_AUTH_KEY` + `GIGACHAT_SCOPE` (GIGACHAT_API_PERS) + `GIGACHAT_MODEL` (GigaChat) — AI spam analysis needs at least one of the two API keys.

## Architecture

Telegram anti-spam bot. Driven by five update types: `chat_member` (joins/leaves), `my_chat_member` (bot's own membership), `callback_query` (captcha answers + DM menu), `message` (stats, service messages, DM commands), `edited_message` (AI spam re-check of edits).

### Update pipeline (`internal/bot/bot.go`)

Long-polling via telego → `th.BotHandler`:
- `th.AnyChatMember()` → `handleChatMember` — captcha kickoff; also cancels the captcha quietly (no kick event) when the user leaves mid-captcha; also invalidates the admin cache on every event, insta-bans known spammers on join and forgives them on manual unban (see §AI spam analysis)
- `th.AnyMyChatMember()` → `handleMyChatMember` — on bot leave: drop chat from registry + cancel/delete its pending captchas; on join/promotion: register chat + post a missing-rights hint (`checkAdminRights`)
- `cap:` callbacks → `handleCallback` — captcha answer
- `capok:` callbacks → `handleApproveCallback` — admin "✅ Впустить" button (manual approve, same path as success)
- `menu:` callbacks → `handleMenuCallback` — DM menu (stats, settings)
- `sv:` callbacks → `handleSpamVoteCallback` — «спам/не спам» voting buttons (AI spam analysis)
- `/stats`, `/greeting` — registered as no-op handlers so the commands are swallowed silently in groups (all management is via the DM menu)
- `/kick`, `/ban` — in-group moderation for chat admins / bot owners (`internal/bot/modcmd.go`); NOT in SetMyCommands (keeps the group "/" menu empty). Target resolved by text_mention entity → `@username` (via cached `user_info`, `UserIDByUsername`) → reply-to target → reply-to the bot's greeting (`GreetingUserByMsg`). Both wipe the target's messages (banRevoke / kickRevoke) + our own greeting + any active vote plashka (`TakeSpamVoteByAuthor`). `/del`|`/delete` (reply) silently deletes the target message + the command itself, zero feedback. `/mute <N[m|h|d]>` (bare N = minutes, cap 365d) — read-only via `RestrictChatMember` with `UntilDate`: Telegram lifts it server-side, no bot-side timers/persistence needed. A non-admin invoking ANY of these gets `punishNonAdmin`: 1-minute mute + "не балуйся" reply — but only on VERIFIED non-admin status (`canManageChatVerified`; a getChatMember error is silently ignored, never punished). All five share `modPrologue`: chat-type/chatAllowed gates, drops commands addressed to other bots (`commandForUs` — telego's CommandEqual ignores the `@bot` suffix), allows anonymous admins (sender_chat == chat). Forum guards: the implicit reply_to_message on a topic root (`ForumTopicCreated != nil`) is ignored by /del and `resolveModTarget` (a bare command in a topic must not target the topic creator); confirmations thread via `threadOf`. `/mute` cancels the target's pending reply-wait (a muted user can't satisfy it); `restrictFor` recomputes until_date on EVERY retry attempt — a long 429 retry_after would otherwise push a 1-minute mute under Telegram's 30s floor and make it permanent
- `/chats`, `/logs`, `/info`, `/start`, `/help` — DM commands
- `privateMessagePredicate` → `handlePrivateText` — greeting-text input flow (see below)
- fallback `HandleMessage` → `handleGroupMessage` — migration branches (before the gate), `chatAllowed` gate (foreign chats must not enter the registry / leak the DM menu), new_chat_members captcha fallback, service-message cleanup, message counting, `maybeAnnounceReturn`, `maybeSpamCheck` hook at the tail
- `HandleEditedMessage` → `handleEditedGroupMessage` — spam-checks edits only (counters/announces untouched — the original already counted); gates: chat type, `chatAllowed`, bots/777000/auto-forward, live-location (edited_message fires every few seconds during broadcast), mid-captcha delete, per-(chat,user) `editCheckCooldown` (edits never grow the message counter, so without it a newcomer could burn LLM quota by re-editing one message forever)

Handler registration order matters — telego runs the first matching predicate and stops. `handlePrivateText` must stay after the command handlers and before `handleGroupMessage`. `bh.Use(th.PanicRecoveryHandler(...))` must stay BEFORE all `bh.Handle*` (middleware and handlers share one ordered route list); it only covers handler chains — the bot's own goroutines are wrapped by `Bot.goSafe` (recover does not cross goroutine boundaries; trade-off: a panicking background loop dies quietly with an Error log instead of crashing the process).

### Captcha lifecycle (`internal/bot/handlers.go`)

1. `handleChatMember` detects `left|kicked → member|restricted`, filters bots/self/channels/disallowed-chats, calls `startCaptcha`; the `join` event is recorded only when `startCaptcha` wins the kickoff (Telegram delivers most joins via BOTH `chat_member` and `new_chat_members` — recording before the dedup double-counts joins and shows phantom "pending" rows in stats). `message.new_chat_members` is the fallback path (some group types) — it also carries the forum `threadID` (`IsTopicMessage`), so forum captchas land in the right topic.
2. `startCaptcha` → `BeginKickoff` dedup lock → async `runCaptcha`: **restrict first** (immediately — every pre-restrict second is a spam window; the restriction is invisible to the user), then sleep `CaptchaDelay` (client render time), then send the keyboard (6 emoji + admin approve row) — the send is wrapped in `retryTG` (429 hits exactly during mass-join waves; a single-shot failure used to release the user with no captcha), then `store.Put` (in-memory, keyed `chatID:userID`), persist to `pending_captchas` (incl. `thread_id`), spawn `waitTimeout`. Three pre-persist aborts unmute via `releaseOnAbort` (a restart cannot restore what was never persisted, so the mute would be permanent): shutdown during the `CaptchaDelay` window, send failure after retries, and `PutPending` failure — the last one also cancels the captcha and lets the user in (fail-open: a DB failure correlates with an imminent restart). Modes (`captcha_mode`): `circles` (default) | `emoji` | `image`. `image` = emoji pool + `SendPhoto` of the correct glyph, mildly distorted (`internal/captcha/image.go`, vendored Noto PNGs via go:embed, pure-Go render); render errors fall back silently to the text emoji prompt — a captcha always goes out.
3. Race resolution: timeout goroutine, `handleCallback`, `handleApproveCallback`, and the user-left branch all call `store.Take()` — whoever wins wraps up; losers are no-ops. `Pending.Cancel()` uses `sync.Once`.
4. Success (correct answer or admin approve): `ResetAttempts`, `UpsertMember(joined_at=now)`, record `pass` event, DM subscribed owners the picked option (`notifyModAction` with `EventPass`; skipped on admin approve — no option was picked), delete captcha message, `release` — which applies the **chat's default permissions from getChat** (not blanket all-true; fallback to all-true only if getChat fails), then `maybeArmReplyWait` (require-reply mode — armed BEFORE the greeting send so the user's first message can't race it), then greeting (custom template or default, sent to the join topic), then `maybeProfileCheck` (AI profile analysis). Greeting templates keep bold/italic: the admin's `message.Entities` are stored as JSON in `chat_settings.greeting_entities` and converted to HTML at render time by `entitiesToHTML` (offsets are UTF-16 — `internal/bot/entities.go`).
5. Fail: `IncrementAttempt` (TTL 24h), record `kick` or `ban` event (with reason `captcha`), delete message, kick if `count < MaxAttempts` else permanent ban.
6. User left mid-captcha: captcha cancelled + message deleted, **no kick event** (stats stay honest); our own post-fail kick is unaffected because `onFail` Takes the pending before kicking.

### Require-reply mode (`internal/bot/replywait.go`)

Per-chat opt-in second verification step after the captcha (`reply_check_enabled`, seconds `reply_check_seconds` default 60, presets 30/60/90/120 in the menu). When on, the greeting is sent ALWAYS (even with the greeting toggle off — the requirement needs an anchor message) with a "write something within N seconds" line, and a `pending_replies` row is armed (restart-safe, mirrors `pending_captchas`; `restorePendingReplies` on startup). ANY message from the user (handleGroupMessage → `replyWaitSatisfied`) clears it; silence past the deadline → `waitReplyTimeout` (detached 10s ctx) kicks/bans on the SAME `attempts` table and `effectiveMaxAttempts` as the captcha (reason `noreply`), deleting the greeting anchor. Left/kicked/banned mid-wait → `cancelReplyWait` (quiet). In-memory `replyStore` (single-winner `Take`, `sync.Once` Cancel) mirrors `captcha.Store`.

### AI profile analysis (`internal/bot/profilecheck.go`)

Runs from `onSuccess` after the greeting: `maybeProfileCheck` gates exactly like `maybeSpamCheck` (whitelist → cross-chat trust → owner/admin → one plashka per author → shared `spamInflight` key), then a goroutine fetches the newcomer's profile via `getChat(userID)` (name/username/bio — the avatar itself never leaves, only `GetUserProfilePhotos` TotalCount) and classifies it with `groq.ProfileSystemPrompt` (deliberately conservative — SPAM only on COMBINED signs; empty bio/no photo is treated as a weak signal, could be privacy). Verdict SPAM → a "X joined but looks suspicious — ban?" plashka on the SAME voting infra (`sv:` callbacks, trust gate, golden vote, margin), persisted as a `spam_votes` row with **`target_msg_id = 0`** (the marker for a profile plashka — there is no target message). Verdict "ban" is the full escalation (banRevoke + AddSpamBanned + banEverywhere) same as a message verdict. `voteView` / `resolveSpamVote` / `notifySpamVerdict` branch on `TargetMsgID == 0`; the `deleteMessage(TargetMsgID)` is guarded (never called with 0). LLM clients generalised: `Classify(ctx, system, facts) (bool, error)` (the message and profile checks differ only by the system prompt); `IsSpam` delegates to it; `classifyVerdict` is the shared provider chain.

### AI spam analysis (`internal/bot/spamcheck.go`, `internal/groq`, `internal/gigachat`)

Per-chat opt-in (`spam_check_enabled`, default off; needs `GROQ_API_KEY` and/or `GIGACHAT_AUTH_KEY`). Provider chain (`classifySpam`): Groq primary (12s sub-budget inside the 30s check ctx — only when the GigaChat fallback is configured, otherwise Groq gets the full 30s); on ANY Groq error — typically its per-minute rate limit — fall back to GigaChat; Groq unset → GigaChat alone; all failed → fail-open. `internal/gigachat`: OAuth token cached ~30 min (+one forced refresh on 401), Russian NUC Mincifry root CA embedded via go:embed (Sber TLS endpoints fail verification without it); both clients share `groq.SystemPrompt` and the lenient `groq.ParseVerdict` (GigaChat has no guaranteed output format). Live check: `GIGACHAT_AUTH_KEY=... go test -run TestLive ./internal/gigachat -v`. Called from the tail of `handleGroupMessage` AND from `handleEditedGroupMessage` (edit re-check, throttled per (chat,user) by `editCheckCooldown` — see pipeline): messages from non-whitelisted users go to the LLM (text/caption + FACTS about media — the files themselves never leave; forward origin; author name, membership age, message total) → binary verdict SPAM/OK (`groq.ParseVerdict`; anything ambiguous is an error → fail-open). Whitelist skips analysis: per-chat `UserMessageTotal > spam_whitelist_msgs` (default 5) first (cheap, covers regulars), then cross-chat trust via `UserMessageTotalsByChat` — clearing the whitelist bar in any ONE chatAllowed chat of the bot grants trust everywhere (the ALLOWED_CHATS filter prevents farming trust in a foreign chat the bot was dragged into; the LLM facts still carry the per-chat total); owners, chat admins (cached 6h in `adminCache`, invalidated on every `chat_member` event). Verdict SPAM → reply with «мне кажется, это спам» + «Да, спам»/«Нет, не спам» buttons, persisted to `spam_votes` (the `prob` column is legacy NOT NULL, always written as 100 and never displayed; `chat_settings.spam_threshold` is likewise legacy — kept in schema/MigrateChat, no setter or reader).

Voting: one ballot per voter (re-press switches), author excluded, trust gate — ballots count only from voters with `UserMessageTotal > spam_whitelist_msgs` in THIS chat (deliberately per-chat, no cross-chat trust; fail-closed on DB error; otherwise a couple of fresh sock-puppet accounts could clear the plashka or rubber-stamp a false LLM verdict into a global ban), margin of `spam_vote_margin` (per-chat, default 3, presets 2/3/5) decides — |yes−no| ≥ N; an admin/owner vote decides instantly ("golden vote", no trust gate). Verdict executor starts with `TakeSpamVote` (atomic DELETE, first caller wins — double-click/race safe). Spam → `banRevoke` (BanChatMember with `RevokeMessages:true`, wipes ALL author's messages) + the bot's own greeting for that user (looked up via the `greetings` table, populated by `maybeSendGreeting`) + `spamban` event; not-spam → delete only the bot's message. Spam verdict also feeds the GLOBAL spammer base: `AddSpamBanned` + `banEverywhere` (single-shot BanChatMember — NOT retryTG: the typical error is "not enough rights", which is permanent, and a retry ladder would only stretch the sweep — in every other allowed group from the `chats` registry; runs in a goroutine AFTER the plashka is removed; `spamban` event only in the verdict chat — otherwise the stats double-count). A join by a known spammer (`IsSpamBanned` in `onUserJoined`) gets an instant `banRevoke` instead of a captcha; on ban failure falls back to the normal captcha; dedup via `BeginKickoff` held for +1 min after the ban (otherwise the duplicate new_chat_members delivery would double the spamban event; the kickoff lock is defer-protected inside the goroutine so a panic can't leave it stuck forever). Manual admin unban anywhere (`kicked→*` by a foreign non-bot hand in `handleChatMember`) forgives: `DeleteSpamBanned`. Owner DM notifications (per-owner toggle `owner_settings.spam_notify`, «🔔» button in the main DM menu, `menu:spamnotify`): suspicion = forward of the flagged message + score card (`notifySpamSuspicion`), verdict = who decided + per-name yes/no ballots (`ListBallots` read BEFORE `TakeSpamVote` — Take wipes them) + list of chats cross-banned (`notifySpamVerdict`). `spamVoteSweepLoop` (hourly + at startup) closes votes older than 24h — past 48h Telegram refuses bot deletions entirely, so never let them age. Groq errors/timeouts are fail-open (message stays, Warn logged). Logging is deliberately verbose (owners-only surface): every check logs the full `facts` string sent to Groq + prob; every button press logs `spam vote ballot` with the voter's name/@username/id and the running tally. Groq call runs in a goroutine on `runCtx`; in-flight dedup per chat:user + one pending vote per author max. Live prompt check: `GROQ_API_KEY=... go test -run TestLive ./internal/groq -v`.

### Flood control (`internal/bot/actions.go`)

Every critical Telegram call retries with backoff and honors `retry_after` on 429 (mass-join scenario): `restrict`, `release`, `chatDefaultPermissions` (getChat), `ban`, `banRevoke`, BOTH halves of `kick` (ban + unban — transient errors must not turn kicks into permabans), and the captcha send in `runCaptcha` (single-shot would release users captcha-less mid-flood). Two ladders: `tgBackoffs` (0/1/2/4s) for most calls, `kickUnbanBackoffs` (0/300/600/900ms) for kick — its whole fail path lives inside `waitTimeout`'s 10s cleanup ctx. `banEverywhere` is deliberately single-shot (see §AI spam analysis); `releaseOnAbort` — see §Context discipline.

### Persistence (`internal/storage/`)

Single SQLite file, pure Go driver (`modernc.org/sqlite`, no CGO). `SetMaxOpenConns(1)`. Schema in `schema.sql` (embedded, idempotent) + additive `ALTER TABLE` migrations in `db.go` that ignore "duplicate column name". **Every new chat_settings/pending_captchas column must be added in BOTH places, and to the `MigrateChat` INSERT — the migrate test checks all settings columns survive.**

Tables:
- `pending_captchas(chat_id, user_id, message_id, correct_idx, expires_at, thread_id)` — active captchas. Deleted on take/timeout/user-left/bot-left.
- `attempts(chat_id, user_id, count, updated_at)` — failure counter, 24h TTL, swept by `attemptsSweepLoop`.
- `events(id, chat_id, user_id, kind, at, reason)` — append-only, `kind ∈ {join,pass,kick,ban,spamban}` (`spamban` — AI-antispam verdict, kept out of the captcha funnel percentages; the «Забанены» stats list merges `ban`+`spamban`). `reason` (NULL for join/pass and old rows): `captcha`|`noreply`|`global`|`mod:<adminID>`|`vote:<id,id,...>` — `humanReason`/`reasonSuffix` render it in stats and owner notifications; `TopFailers`/`EventUsers` carry the last reason.
- `members(chat_id, user_id, joined_at)` — upserted on captcha pass; drives newcomer classification + silence baseline.
- `message_counts(chat_id, day, newcomer_count, oldtimer_count)` — daily aggregates.
- `user_activity`, `user_message_counts` — silence detection / top writers.
- `user_info(user_id, …)` — display-name cache for mentions.
- `chats(chat_id, title, type)` — registry for the DM menu; row removed when the bot leaves.
- `chat_settings(chat_id, greeting_enabled, max_attempts, captcha_timeout_seconds, daily_stats_enabled, daily_stats_utc_hour, last_daily_stats_day, captcha_mode, greeting_text, greeting_entities, silent_announce_enabled, spam_check_enabled, spam_threshold (legacy, unused), spam_whitelist_msgs, spam_vote_margin, reply_check_enabled, reply_check_seconds)` — per-chat overrides; NULL = global default. Resolved via `effective*` helpers in `access.go` (spam ones are pure funcs in `spamcheck.go` over a loaded `ChatSettings`).
- `pending_replies(chat_id, user_id, expires_at)` — active require-reply waits; restart-safe, restored by `restorePendingReplies`.
- `spam_votes(chat_id, bot_msg_id, target_msg_id, author_id, prob, created_at)` + `spam_ballots(chat_id, bot_msg_id, voter_id, is_spam)` — active «спам/не спам» votes; all state in SQLite (restart-safe), rows removed by `TakeSpamVote`.
- `greetings(chat_id, user_id, message_id, sent_at)` — bot greeting ids so a spam-ban can delete the «Добро пожаловать» too; upserted per re-join, pruned hourly past 48h (Telegram won't delete older messages anyway).
- `spam_banned(user_id PK, chat_id, at)` — global spammer base (chat_id = verdict origin); cleared by `DeleteSpamBanned` when an admin manually unbans the user in any chat.
- `owner_settings(owner_id PK, spam_notify, mod_notify, daily_report, last_report_day)` — global per-USER prefs (NOT per-chat, not in `MigrateChat`; the name is historical — `daily_report` rows can belong to chat admins, not just owners). `mod_notify` (🛡 button, `menu:modnotify`): DM on every kick/ban with the human reason (`notifyModAction`, async via `goSafe` — captcha fails incl. picked-vs-correct option, no-reply, `/kick`|`/ban`, known-spammer join; vote verdicts stay under `spam_notify`) + captcha passes with the picked option (`EventPass`, skipped on admin approve). `daily_report` (📬 button, `menu:dreport` — the only main-menu item available to non-owners, gated by `canGetDailyReport` = owner or admin of ≥1 registered chat): morning DM report for yesterday, one compact `reportLine` per chat of `userChats` (owner → all), sent from the digest loop (`maybeSendDMReports`); `last_report_day` is the per-user sent marker; NOT set on send failure or when `userChats` comes back empty (could be a transient getChatMember error) → retried till midnight; a «Forbidden» send error (user blocked the bot's DM) auto-unsubscribes; the report body is capped by `reportRuneBudget` («… и ещё N чатов»).

Write-through caches (`internal/bot/cache.go`): `rememberChat`/`rememberUser` skip the DB write when the cached value is unchanged — use these instead of calling `db.RememberChat`/`db.RememberUser` directly from hot paths.

### Stats semantics (IMPORTANT)

Events are counted by unix time (`at >= from AND at < until`), messages by calendar day (`day >= fromDay AND day < untilDay`) — **both upper bounds exclusive**. Days are cut in `storage.StatsLocation` (MSK = fixed UTC+3, no DST in Russia since 2014) via `storage.DayOf` — the ONLY day-formatting site; the offset lives ONLY in `storage.MSKOffsetHours` (feeds StatsLocation, the digest-gate SQL shift, and menu.go's MSK hour labels). `statsRange(p, now)` returns MSK-calendar-aligned windows (day = today since 00:00 MSK, yesterday = [yesterday 00:00, today 00:00) — the only period whose `until` is TODAY's midnight, week = 7 calendar days, month = 30) precisely so both counts cover the same range. The daily digest passes [yesterday 00:00, today 00:00) MSK and labels it «вчера» via `renderStats`'s label parameter. Don't reintroduce rolling `now-24h` windows — they desync event vs message counts. Historical rows written before the MSK switch are keyed by UTC days; messages sent 00:00–03:00 MSK in the past sit in the previous day — accepted one-off drift.

### DM menu (`internal/bot/menu.go`)

Callback formats: `menu:main|help|add|chats|logs`, `menu:aicheck` (owner-only LLM connectivity check — real test request to each provider separately, result edits the «⏳…» message; `internal/bot/aicheck.go`), `menu:spamnotify` / `menu:modnotify` (owner-only global toggles for spam / moderation DM notifications), `menu:dreport` (owner OR chat-admin toggle for the morning DM report — see §Persistence `owner_settings`), `menu:stats:<chat>:<period>` (`period ∈ {day,yesterday,daybefore,week,month,all}`), `menu:settings:<chat>`, toggles `menu:gr|daily|sil|spam|rpl:<chat>` (`rpl` = require-reply), presets `menu:max|tmo|hour|swl|svm|rplt:<chat>:<val>` (whitelist msgs / vote margin / reply seconds), `menu:cmode:<chat>:<mode>`, `menu:grtxt:<chat>` (arms greeting-text input). Access via `canManageChat` (bot owner or chat admin via getChatMember).

Greeting-text input flow: `menu:grtxt` stores `userID→chatID` in `Bot.greetInput`; the next private message (handled by `handlePrivateText`) becomes the template. `-` resets to default, any `/command` aborts, 500-rune cap. Templates are HTML-escaped at render time; `{name}` is replaced with the mention markup after escaping (`renderGreeting`).

Button labels: always truncate with `truncateLabel` (rune-safe) — byte slicing corrupts Cyrillic titles and Telegram rejects the whole keyboard on invalid UTF-8.

### Daily digest (`internal/bot/daily.go`)

`dailyDigestLoop` ticks every 5 min; `ChatsNeedingDailyStats` gates on per-chat hour (override or `DAILY_STATS_UTC_HOUR`) + `last_daily_stats_day`. The hour is STORED in UTC (menu presets/`mskHourLabel` compatibility) but the gate compares in MSK via the SQL shift `(hour+MSKOffsetHours)%24` (bound parameter) — the gate hour and the MSK day marker must live in the same zone, otherwise the day flips at 21:00 UTC while the gate is already open and every digest permanently drifts to midnight MSK. The digest window is `statsRange(periodYesterday, now)` — the same source as the menu's «Вчера» button, so the two can never diverge; the sent-marker is the day of `until`. Empty digests are skipped but still marked sent. The same loop tail runs `maybeSendDMReports` — the per-user morning DM report (subscribers via `owner_settings.daily_report`, global `DAILY_STATS_UTC_HOUR` gate, same yesterday window, always sent even on an empty day — user's choice).

### Restart behavior

`restorePending` reloads `pending_captchas` (incl. thread_id) into the store with original deadlines; already-expired rows get a 1-second grace timer → auto-kick. Mid-captcha users survive restarts. `reconcileChats` runs once at startup and drops registry rows for chats the bot is no longer in (BOT_TOKEN switched to another bot, or kicked while offline — `my_chat_member` never fires for either).

### Context discipline

- `Bot.runCtx` — root ctx; long-lived/async work (captcha flow, sweeper, digests, DB writes from callbacks).
- Handler `*th.Context` — short-lived replies only (AnswerCallbackQuery, menu edits).
- `waitTimeout` cleanup uses a detached 10s `context.Background()` so shutdown doesn't drop kicks/bans.
- `releaseOnAbort` — full retry budget on a live ctx; detached 15s `context.Background()` when the caller's ctx is dead (shutdown) — enough for both retryTG ladders inside `release` (getChat + restrict).

## When making changes

- New update types → add to `AllowedUpdates` in `Bot.Run`, otherwise Telegram doesn't deliver them.
- New background goroutines → launch via `b.goSafe(name, fn)`, never bare `go` — recover does not cross goroutine boundaries, and one panic would kill the whole process.
- New group-message code paths → put them behind the `chatAllowed` gate (see `handleGroupMessage`/`handleEditedGroupMessage`) — foreign chats must not enter the registry, stats, or the DM menu.
- Callback data formats: captcha `cap:<userID>:<optIdx>`, approve `capok:<userID>`, menu `menu:...`, spam vote `sv:<1|0>` (chat/msg come from the callback's message) — update both formatter and parser sides. Note `th.CallbackDataPrefix("cap:")` does NOT match `capok:` (prefix includes the colon).
- Schema changes: `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ... ADD COLUMN` in **both** `schema.sql` and `db.go` migrations, **plus** `MigrateChat` if the table is per-chat keyed.
- New event kinds: `EventKind` const block + `QueryStats` switch.
- Admin-gated UI: reuse `canManageChat` (covers owner + chat admin).
- Stats privacy: `message_counts` is aggregate-only by design. Per-user tables (`user_activity`, `user_message_counts`) exist for tops/silence — keep new per-user data behind the same "admins only" access.
- Messages to forum supergroups: thread the `threadID` through (see `onUserJoined` → `runCaptcha` → `Pending.ThreadID` → greeting) or the message lands in General.
- Adding an emoji to the pool → drop its glyph PNG into `internal/captcha/assets/` (`TestAllEmojiGlyphsPresent` catches pool/assets drift).
- `gofmt -w .` before committing — CI/tests assume formatted code.
