# AntiSpamBot

Telegram-бот на Go: проверяет новичков капчей, помогает модерировать чаты и ведёт статистику. Работает через long polling; состояние хранится в SQLite.

## Возможности

- Три режима капчи: цветные кружки, эмодзи, картинка. Напоминания и порог бана настраиваются для каждого чата.
- После капчи: ничего, приветствие или приветствие с обязательным осмысленным ответом. Дополнительно — текстовый карантин новичка.
- Модерация, ручной пропуск, доверенные пользователи и голосование по жалобе `/spam`.
- ИИ-антиспам сообщений и профилей: Groq → Gemini → GigaChat; порядок задаётся через env. Подозрение выносится на голосование, голос админа решает сразу. Подтверждённый локальный спам-бан пополняет общую базу и запускает кросс-бан в других обслуживаемых чатах.
- Статистика и ежедневные сводки по московским календарным дням. «В процессе» показывает входы выбранного периода без исхода к его концу. Для старых входов бот оценивает исход по истории событий. Настройки доступны через личное меню.
- Уведомления владельцам, ответ в чат из ЛС от имени бота, наблюдение за удалением/правками ответа новичка.
- Восстановление незавершённых проверок после рестарта, форумные топики и опциональные эфемерные сообщения.

История версий — [CHANGELOG.md](CHANGELOG.md), в боте — `/whatsnew`.

## Запуск

1. Создай бота у [@BotFather](https://t.me/BotFather), получи токен и выключи Group Privacy.
2. Скопируй настройки и заполни `BOT_TOKEN`. Укажи `OWNER_IDS`, если нужно подтверждать добавление в новые чаты и управлять всеми чатами.

```sh
cp .env.example .env
```

Владельцы должны хотя бы раз написать боту `/start`, чтобы он мог отправлять им сообщения. Для разработки используй отдельного бота и тестовый чат.

Локально нужен Go по [go.mod](go.mod):

```sh
go mod download
make run
```

`.env` подхватывается автоматически. База по умолчанию — `./bot.db`. Makefile включает обязательный для проекта build tag `stdjson`.

Для запуска готового прод-образа нужен Docker Compose v2:

```sh
docker compose pull bot
docker compose up -d --no-build
docker compose logs -f bot
```

Для сборки из текущих исходников — `make docker-up`. Версия в бинаре проставляется Makefile/CI; непосредственная сборка через compose без `VERSION` даёт `dev`.

Добавь бота администратором группы с правами блокировки участников и удаления сообщений. Если заданы владельцы, новый чат, добавленный другим человеком, ждёт их одобрения в ЛС; без `OWNER_IDS` новые чаты одобряются автоматически.

В ЛС: `/start` → «Мои чаты» → чат → «Настройки». Владелец управляет всеми обслуживаемыми чатами, админ — своими. Если задан `ALLOWED_CHATS`, при превращении группы в супергруппу новый ID нужно добавить в список.

Перед выходом бота через меню заверши активные капчи: впусти или исключи участников. Пока есть незавершённая проверка входа, бот остаётся в чате, чтобы не оставить человеку бессрочный мут.

## Команды

Полный список и пояснения — `/help`. Основные:

| Команды | Доступ и назначение |
|---|---|
| `/start`, `/chats` | ЛС: меню, доступные чаты и их настройки |
| `/help`, `/whatsnew` | Справка и изменения; доступны также в группе |
| `/info` в ЛС | Владелец бота: версия, время запуска и аптайм |
| `/info` в группе | Админ или владелец: карточка участника с датой входа, активностью и нарушениями |
| `/logs` | Владелец бота в ЛС: файл журнала |
| `/kick`, `/ban`, `/mute N` | Админ/владелец в группе: кик, бан, мут; `N` — минуты, также `10m`, `2h`, `1d` |
| `/del` (`/delete`) | Админ/владелец: удалить сообщение реплаем |
| `/unban`, `/unmute`, `/whitelist` | Админ/владелец: восстановление в текущем чате. `/whitelist` даёт вход без капчи |
| `/fullunban` | Только владелец бота. Снимает баны в обслуживаемых чатах и очищает общую запись спамера |
| `/trust` | Админ/владелец: досрочно снять карантин |
| `/spam` | Жалоба реплаем: доверенный участник открывает голосование, админ/владелец сразу запускает спам-бан |
| `/replywithbot` (`/rwb`) | Только владелец: ответ от имени бота в группе; в ЛС достаточно ответа реплаем на пересланное ботом сообщение или связанную карточку |

Модерация принимает реплай или известный боту `@username`; некоторые команды без цели предлагают список последних действий. `/del` и `/spam` требуют реплая, `/replywithbot` — реплая и текста ответа. `/mute` требует срок. Ограничение прав участника и их восстановление через Telegram Bot API требуют супергруппы. Это относится к капче, карантину, `/mute` и `/unmute`. Кик и бан стирают сообщения цели, поэтому для проверки используй тестовый чат. [Telegram Bot API](https://core.telegram.org/bots/api#restrictchatmember)

## Настройки

Полный список env с дефолтами — [.env.example](.env.example); разбор и валидация — [internal/config/config.go](internal/config/config.go). Изменения env применяются после перезапуска. Настройки отдельного чата меняются через меню.

| Группа | Переменные |
|---|---|
| Доступ | `BOT_TOKEN`, `OWNER_IDS`, `ALLOWED_CHATS` |
| Дефолты капчи | `CAPTCHA_STAGE_MINUTES`, `MAX_ATTEMPTS`, `CAPTCHA_DELAY_MS` |
| Статистика | `NEWCOMER_DAYS`, `SILENT_ANNOUNCE_DAYS`, `DAILY_STATS_UTC_HOUR` |
| Хранение и логи | `DB_PATH`, `LOG_LEVEL`, `LOG_FILE` |
| ИИ | Ключи/модели `GROQ_*`, `GEMINI_*`, `GIGACHAT_*`, порядок `AI_PROVIDER_ORDER` |
| Захват сообщений | `MESSAGE_CAPTURE_ENABLED`, `ARCHIVE_DIR`, `MESSAGE_ARCHIVE_HOT_DAYS` |
| Наблюдение за ответом | `REPLY_WATCH_ENABLED`, `REPLY_WATCH_CHAT_ID` |

Для ИИ нужен хотя бы один ключ и включённый антиспам в настройках чата. Ошибка всех провайдеров не приводит к наказанию.

## Данные и приватность

- SQLite хранит события модерации, счётчики, ID и имена пользователей, настройки и незавершённые проверки. Бот также временно хранит ID обработанных обновлений, пока Telegram их не подтвердит. Статистика и управление чатами доступны владельцам и соответствующим админам.
- При включённом ИИ-антиспаме провайдерам передаются текст или подпись сообщения и сведения об авторе. Для реплая это также обрезанный текст или подпись цитируемого сообщения и доступные имя и username его автора. Если есть внешняя цитата, запрос может включать её текст и сведения об источнике. Проверка профиля включает доступное bio и количество фото. Медиа описываются по типу вложения. Журнал владельцев содержит факты этих ИИ-проверок, включая цитату и сведения о её авторе.
- `MESSAGE_CAPTURE_ENABLED` по умолчанию выключен. При включении сохраняет текстовый след сообщений и правок, включая сведения о реплаях. После горячего окна данные переходят в дневные `.jsonl.zst`; автоматического удаления архивов нет. Выключение захвата уже накопленные данные не удаляет.
- `REPLY_WATCH_ENABLED` по умолчанию включён: снимок ответа новичка хранится отдельно от общего захвата. Пробы копируют сообщение, включая медиа при его наличии, в служебный чат. Бот сохраняет возвращённый Telegram ID копии и удаляет её. При сбое удаления новые пробы ждут подтверждённой очистки, которая продолжается после рестарта и при выключенном наблюдении. Если Telegram создал копию, но не вернул её ID, копию может понадобиться удалить вручную. Перед каждой пробой бот проверяет настроенный личный диалог или закрытую служебную группу без публичных имён и с правом удаления. По умолчанию и при недоступности настроенного назначения используется ЛС владельца с наименьшим ID. Если ЛС недоступен, проба откладывается. Владельцы получают уведомления об удалениях/правках.
- Сообщения также могут пересылаться владельцам в уведомлениях о спаме и ответах новичков. Отключённый общий захват не отключает ИИ-логи, уведомления и reply-watch. Перед включением этих функций предупреди участников.

## Эксплуатация

Compose хранит БД, лог и архивы в volume `bot-data`: `/data/bot.db`, `/data/bot.log`, `/data/archive`. `docker compose down` сохраняет данные; `down -v` удаляет volume.

Обновление готового образа:

```sh
docker compose pull bot
docker compose up -d --no-build
```

[CI](.github/workflows/ci.yml) проверяет форматирование, vet, уязвимости, тесты с race detector и сборку. После успешных проверок push в `main` публикует `ghcr.io/menand/antispambot:latest` и тег версии.
[scripts/auto-deploy.sh](scripts/auto-deploy.sh) предназначен для Linux-сервера: забирает образ, проверяет запуск и при жёстком сбое пытается вернуть предыдущий образ. Пример cron (путь замени своим):

```cron
* * * * * /path/to/AntiSpamBot/scripts/auto-deploy.sh >> /var/log/antispam-deploy.log 2>&1
```

Установи `auto-deploy.sh` и `deploy-notify.sh` в существующую рабочую копию, из которой cron запускает Compose. Перед выбором нового выпуска загрузчик обновляет только ссылку `origin/main` без тегов. Рабочая копия остаётся на установленной ревизии. Compose и скрипты применения берутся по OCI-метке ревизии скачанного образа. Эта ревизия должна быть доступна в истории `origin/main`. Неизменившийся образ не вызывает уведомлений. При ошибке загрузки Git или образа тик завершается до запуска Compose.

Перед первой заменой работающего контейнера скрипт сохраняет в `/var/lib/antispam/releases` его digest и Compose из ревизии образа. Для перехода нужны digest, OCI-метка, локально доступный образ, а также метка проекта и том контейнера. При отсутствии этих данных обновление откладывается. При установке с нуля скрипт записывает `pending` до запуска Compose. После остановки следующий тик сначала сверяет сохранённый digest, том `<проект>_bot-data` и экземпляр контейнера. Указатель `current` появляется после успешной проверки готовности. Храни локальные образы и комплекты для завершения установки и отката. Compose запускается с сохранённым именем проекта и томом `/data`, а рабочий каталог проекта и `.env` остаются в исходной рабочей копии.

При любой ошибке применения, включая отказ Compose после остановки старого контейнера, скрипт сохраняет задачу отката и повторно применяет сохранённые Compose и digest. Если откат прервался или завершился ошибкой, cron продолжает его до загрузки нового выпуска. Запуск и откат проверяют образ, том и отсутствие перезапусков. Готовность подтверждается между 35-й и 120-й секундами по свежему heartbeat текущего процесса после успешного `getUpdates`. Образы предыдущих версий дают гарантию по своему протоколу heartbeat. При работе с containerd сверяется manifest нужной платформы. Ошибка дополнительного вызова `getMe` даёт предупреждение.

После подтверждения скрипт сохраняет текущий комплект, предыдущий выпуск с другим digest и комплект незавершённого запуска. Для остальных комплектов этого проекта ссылка на образ удаляется, когда её не использует другой комплект или контейнер. Ошибка очистки оставляет подтверждённый выпуск действующим. Карантин продолжает блокировать повторное применение отклонённых образов.

Уведомления формируются через [scripts/deploy-notify.sh](scripts/deploy-notify.sh): версии до/после, краткие изменения и результат проверок. CI записывает версию и commit SHA в OCI-метки образа; описание читается из `CHANGELOG.md` этой ревизии, а не из текущего HEAD сервера. Пересборка того же кода с новыми базами Go/Alpine обозначается отдельно. У старых образов без метаданных версия может быть неизвестна. Подробные изменения доступны через `/whatsnew`; этот экран показывает версию запущенного бинаря.

При изменении метки Alpine скрипт читает `/etc/alpine-release` из старого и нового образа в изолированных временных контейнерах без сети и тома с данными бота. Уведомление показывает найденные версии и ссылку на официальный журнал пакетов соответствующего выпуска Alpine; этот журнал охватывает все пакеты выпуска, а не только изменившиеся в образе бота. Если старый образ или файл версии недоступен, вместо догадки выводится «неизвестна».

На время ручного отката останови cron, иначе он снова подтянет `latest`. Совместимость старого бинаря с уже обновлённой БД требует отдельной проверки.

Проверка баз и сборка прод-образа используют manifest `linux/amd64`. Изменения образов для других архитектур не запускают пересборку; CI закрепляет выбранные digest через контексты сборки. При первом переходе со старых меток общего OCI-индекса требуется одна пересборка для обновления меток.

### Резервная копия и восстановление

Команды для Linux-хоста, где запущен локальный Docker daemon. Выполняй их из каталога Compose с доступом к файлам Docker volume. Установи `sqlite3` на хосте. В образе бота есть `msgtool`, а `sqlite3` отсутствует. Для проверки на хосте собери `bin/msgtool` командой `make build`.

Для согласованной копии приостанови минутный cron автодеплоя, затем останови сервис через `docker compose stop bot`. Остановленный контейнер сохраняет привязку тома. В примере `/data` внутри контейнера соответствует `$data_dir` на хосте, а резервная копия записывается в отдельный каталог.

```sh
set -e
data_volume=$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}' menand-antispam)
test -n "$data_volume"
data_dir=$(docker volume inspect --format '{{.Mountpoint}}' "$data_volume")
umask 077
backup_dir=$(mktemp -d /var/backups/antispam.XXXXXX)
sqlite3 "$data_dir/bot.db" ".backup '$backup_dir/bot.db'"
mkdir "$backup_dir/archive"
for file in "$data_dir"/archive/*.jsonl.zst; do
    [ -f "$file" ] || continue
    cp "$file" "$backup_dir/archive/"
done
cp .env "$backup_dir/.env"
```

После копирования запусти прежний контейнер через `docker compose start bot` и верни cron. Бэкап содержит БД SQLite с учётом WAL, завершённые архивы и защищённую копию `.env`. Если архиватор прервался после записи архива и до удаления строк, `msgtool` уберёт точные совпадения при чтении.

Сначала восстанови файлы в отдельный каталог. Переключи только проверочную копию в режим DELETE, чтобы её можно было открыть на чтение без файлов WAL и SHM. При рабочем запуске бот сам включит WAL. Подставь путь к выбранному бэкапу в `backup_dir`, если используешь новую оболочку.

```sh
set -e
restore_dir=$(mktemp -d /tmp/antispam-restore.XXXXXX)
cp "$backup_dir/bot.db" "$restore_dir/bot.db"
cp -R "$backup_dir/archive" "$restore_dir/archive"
test "$(sqlite3 "$restore_dir/bot.db" 'PRAGMA journal_mode=DELETE;')" = delete
test "$(sqlite3 -readonly "$restore_dir/bot.db" 'PRAGMA integrity_check;')" = ok
bin/msgtool -verify-archive -archive "$restore_dir/archive"
```

Проверка архива читает все дневные файлы без вывода сообщений. Повреждённый файл останавливает восстановление. Пустой каталог архивов допустим для новой установки.

Для рабочего восстановления снова приостанови cron и останови сервис. Сохрани текущие файлы в томе, затем установи проверенные БД и архивы с владельцем каталога данных. Проверь выход каждой команды перед запуском сервиса.

```sh
set -e
bin/msgtool -verify-archive -archive "$restore_dir/archive"
data_owner=$(stat -c '%u:%g' "$data_dir")
before_restore=$(mktemp -d "$data_dir/.before-restore.XXXXXX")
for name in bot.db bot.db-wal bot.db-shm archive; do
    [ ! -e "$data_dir/$name" ] || mv "$data_dir/$name" "$before_restore/"
done
cp "$restore_dir/bot.db" "$data_dir/bot.db"
cp -R "$restore_dir/archive" "$data_dir/archive"
chown -R "$data_owner" "$data_dir/bot.db" "$data_dir/archive"
```

Верни сервис и cron после проверки. Для отката приложения сначала проверь, что предыдущий бинарь открывает копию обновлённой БД и выполняет нужные операции чтения и записи. Если схема несовместима, откатывай образ вместе с согласованной копией БД и архивов от соответствующего выпуска.

После перехода группы в супергруппу `msgtool -chat <новый-ID>` читает горячие и архивные записи по обоим ID, пользуясь связью из SQLite. В выводе остаются исходные ID чата и сообщения, поэтому совпавшие номера сообщений из двух чатов различимы.

Если бот не реагирует, проверь его права в чате, одобрение владельцем, `ALLOWED_CHATS`, Privacy Mode и `docker compose logs --tail=100 bot`.

## Разработка и ревью

```sh
make build            # bin/bot и bin/msgtool
make vet
go test -tags stdjson -race -count=1 -skip '^TestLive' ./...
gofmt -l .            # пустой вывод = код отформатирован
```

`make test` запускает race-тесты, включая `TestLive*`, если экспортированы ключи провайдеров. Команда выше исключает реальные запросы к LLM. Для `make vuln` используй `govulncheck` v1.9.0 из CI. Та же проверка доступна командой `go run golang.org/x/vuln/cmd/govulncheck@v1.9.0 -tags stdjson ./...`.

Для `make lint` нужен `golangci-lint` с поддержкой Go 1.27, начиная с v2.13.0. Проверь через `golangci-lint version`, что сам инструмент собран с Go 1.27 или новее. [Поддержка версий Go](https://golangci-lint.run/docs/welcome/faq/#which-go-versions-are-supported) · [Выпуск v2.13.0](https://github.com/golangci/golangci-lint/releases/tag/v2.13.0)

- [AGENTS.md](AGENTS.md) — постоянные правила проекта: карта кода, команды и ограничения.
- [.agents/skills/full-review/SKILL.md](.agents/skills/full-review/SKILL.md) — сценарий комплексного ревью кода; укажи skill `full-review` и область (рабочие изменения, ветка относительно базы, коммит или весь проект). В CLI/IDE можно использовать `$full-review`.

По [документации Codex](https://learn.chatgpt.com/docs/agent-configuration/agents-md), инструкции собираются при старте: сначала глобальные из `CODEX_HOME` (обычно `~/.codex`), затем от корня проекта до рабочего каталога. Глобально выбирается `AGENTS.override.md` или `AGENTS.md`; в каждом каталоге проекта — первый непустой файл в порядке `AGENTS.override.md`, `AGENTS.md`, настроенные fallback-имена. Более близкие к рабочему каталогу инструкции имеют приоритет. В этом репозитории достаточно корневого `AGENTS.md`; локальные правила нужны только при отличающихся требованиях каталога. После изменения `AGENTS.md` начни новый чат из корня проекта, чтобы заново загрузить инструкции.

Codex обнаруживает [skills в `.agents/skills/`](https://learn.chatgpt.com/docs/build-skills): имя и описание доступны при выборе, тело `SKILL.md` читается при применении. Остальные Markdown-файлы и документы по ссылкам нужно читать явно по задаче. `CLAUDE.md`, `agent.md`, роли OpenCode и правила Cursor/Copilot не становятся инструкциями Codex только из-за имени. Общие правила держим в `AGENTS.md`, а порядок ревью описан в skill. [Best practices](https://learn.chatgpt.com/guides/best-practices)

Проектная `.codex/config.toml` для этой структуры не требуется; её добавляют при необходимости общих настроек инструмента, а не для дублирования Markdown-правил. Codex применяет её только в доверенных проектах; личные настройки и разрешения остаются вне репозитория ([Config basics](https://learn.chatgpt.com/docs/config-file/config-basic)). OpenCode также поддерживает [корневой `AGENTS.md`](https://docs.opencode.ai/docs/rules/) и [`.agents/skills/`](https://docs.opencode.ai/docs/skills/); отдельная копия общих правил ему не нужна. Его пользовательская конфигурация и описания специализированных агентов автоматически в Codex не переносятся.
